# Обучение Blender-модели — как это работает

Коротко: `Qwen2.5-1.5B-Instruct` дообучается (QLoRA) на сгенерированных
диалогах, где ассистент **сначала объясняет план**, затем одним вызовом
инструмента строит **детализированную сцену**, проверяет её через `look` и
пишет резюме. Готовые веса сливаются с базой и превращаются в `.ymq`-кэш для
Rust-движка.

```
generate_3d_dataset.py  ──►  data/train.jsonl + data/val.jsonl
        │                        │
        │                        ▼
        │                train_lora.py (QLoRA, chunked loss)
        │                        │
        ▼                        ▼
system_prompt.txt      output/lora_adapter ──► models/Qwen2.5-1.5B-BlenderMCP
   (правила)                                      │
        │                                        ▼
        └──────────► CLI / server ───────►  model.q4km.ymq
```

## Файлы

| Файл | Что делает |
| --- | --- |
| `generate_3d_dataset.py` | Единственный источник датасета и правил. Собирает рецепты сцен, проверяет каждый bpy-скрипт через `ast.parse`, пишет `train.jsonl`, `val.jsonl` и `system_prompt.txt`. |
| `system_prompt.txt` | Только правила рабочего цикла. Rust CLI/сервер читают его и дописывают **4 компактные схемы** из `blender_training_tools()` — те самые, на которых училась модель (живые 9 схем занимают ~5К токенов и давали prefill 132 с вместо 23 с). |
| `bpy_preamble.py` | Фиксированная библиотека bpy-helpers, подставляемая вместо маркера `# YESMAN_STUDIO`. Helpers терпимы к перепутанным аргументам (`*a` + coercion по типу), а тело сцены исполняется по отдельным statement'ам: одна опечатка модели пропускается, остальная сцена достраивается. |
| `data/*.jsonl` | ChatML-диалоги `{"messages": [...]}`. |
| `train_lora.py` | Токенизация, маскирование лосса, QLoRA-обучение, слияние адаптера. |
| `mcp_tools_schema.json` | Снимок реальных инструментов `mcp-for-blender` для справки (в обучении не используется). |
| `../tools/train_blender.sh` | Весь пайплайн одной командой. |

## Устройство датасета

### Рецепт (`Recipe`)

Один рецепт = одна детальная сцена:

- `prompts_ru` / `prompts_en` — 4–6 перефразированных запросов;
- `plan_ru` / `plan_en` — явный план из 3–6 пунктов (чему учится модель);
- `summary_*` — финальное резюме;
- `materials` — строки `M(...)`, создающие PBR-материалы;
- `body` — компактный параметрический bpy-код с циклами;
- `camera` / `target` — ракурс студийной камеры.

Ответ модели начинается с одной строки `# YESMAN_STUDIO`, а не с 4.6 КБ
boilerplate. При выполнении `crates/yesman-model/src/mcp.rs` заменяет этот
маркер на `bpy_preamble.py` — заранее проверенную библиотеку helpers
(`M` материалы, `B/C/S/K/T` примитивы, `V` кривые Безье, `L` вращение
профиля, `ST` земля + 3 area-источника + камера). Это критично: 1.5B модель
неспособна дословно воспроизвести длинный преамбул и начинает выдумывать
несуществующие `bpy`-API. Теперь она учит только компактное тело сцены
(~1.8 КБ), а валидность библиотеки гарантируется рантаймом. Расширение
работает и для прямых `execute_blender_code`, и для JS-строки OpenCode
Code Mode (где `\n` в маркере заэкранирован).

### Форматы вызова

Сервер обслуживает два типа клиентов, поэтому в выборке есть оба:

| Формат | System prompt | Вызов |
| --- | --- | --- |
| Прямой MCP (CLI `--blender`) | `RULES` + 4 инструмента | `execute_blender_code`, `look`, `get_scene_info`, `get_addon_status` |
| OpenCode Code Mode (`/v1/responses`) | `RULES` + инструмент `execute` | `execute` с JS `await tools.blender.execute_blender_code({ code: ... })` |

Модель учится выбирать формат по списку инструментов в системном промпте.

### Типы примеров

1. **Одноходовой**: `plan + <tool_call>` (большинство).
2. **Многоходовой агентный цикл**: `plan + вызов → <tool_response> → look → <tool_response> → резюме`.

В `train_lora.py` лосс считается **по всем assistant-ходам** (раньше
маскировалось всё, кроме последнего ответа, поэтому план и резюме не
обучались).

## Почему `ChunkedLossTrainer`

При 3.5k токенов полные логиты `[T, 151936]` + fp32-копия для
cross-entropy занимают >3 ГБ VRAM — на RTX 3060 (6 ГБ) это OOM. Тренер берёт
`last_hidden_state` декодера и применяет `lm_head` + `cross_entropy`
порциями по `--loss-chunk-size` (по умолчанию 512) токенов. Градиенты идут
через все токены, пиковая память под логиты ограничена chunk-ом.

Примеры, которые не влезают в `--max-seq-len` (по умолчанию 3840),
**отбрасываются**, а не обрезаются: обрезанный посредине bpy-скрипт учил
модель останавливаться на полпути — это и была одна из причин «малой
детализации».

## Команды

```bash
# только статистика по датасету, без загрузки весов
training/.venv/bin/python training/train_lora.py --dry-run

# проверить сгенерированные скрипты в headless Blender (не трогает живую сцену)
python3 training/generate_3d_dataset.py --check-blender --blender-limit 11

# пробный прогон на 2 шага (проверка VRAM), без слияния
training/.venv/bin/python training/train_lora.py --max-steps 2 --skip-merge

# весь пайплайн: датасет → обучение → слияние → .ymq → smoke test
bash tools/train_blender.sh

# только слить уже обученный адаптер
training/.venv/bin/python training/train_lora.py --merge-only
```

## Верифицированные рецепты (`recipes.json`)

Генератор additionally пишет `training/recipes.json`: 11 проверенных тел сцен
и набор характерных имён объектов/материалов для каждого рецепта.

Практика показала, что Qwen2.5-1.5B после LoRA на 11 рецептах надёжно
воспроизводит **имена** объектов (`MouseBody`, `MouseCable`, `Carapace`...), но
путает координаты и размеры. Поэтому `crates/yesman-model/src/mcp.rs`
(`repair_scene_body`) сопоставляет имена из сгенерированного тела с библиотекой
и при уверенном совпадении подменяет тело на проверенное. Модель по-прежнему
пишет план и выбирает, что строить; геометрия берётся из проверенного скрипта.

Плюс рантайм: убирает объекты с 0 граней, подгоняет размер земли под bbox
мешей и наводит вьюпорт на главный объект (центр из `ST(cam, target)`).

**Ограничение:** произвольного нового объекта модель не придумает — она
выбирает один из рецептов. Чтобы добавить объект, допишите `Recipe` в
`generate_3d_dataset.py`, сгенерируйте датасет и переобучите
(`bash tools/train_blender.sh --epochs 8`). Альтернатива — кратно больший
корпус реальных bpy-скриптов и модель побольше.

Проверить соответствие: `python3 tools/validate_generation.py /tmp/gen.txt`
печатает `recipe repair: <key>` и число созданных объектов.

## Что изменилось относительно старой версии

| Было | Стало |
| --- | --- |
| ~36 уникальных скриптов, в основном примитивы | 11 студийных рецептов, 30–40 именованных деталей, Bevel/WeightedNormal, процедурные PBR, свет и камера |
| Модель должна была выдавать 6 КБ boilerplate и галлюцинировала bpy-API | Маркер `# YESMAN_STUDIO` + короткое тело; библиотеку подставляет рантайм |
| Ответ = голый `<tool_call>` | План → код → проверка `look` → резюме |
| Скрипты до 8.5k токенов при `max-seq-len=1400` → тихое обрезание | Скрипты ~2.2k токенов, `max-seq-len=3840`, отбрасывание вместо обрезания, chunked loss |
| Лосс только на последнем assistant-ходе | Лосс на всех assistant-ходах |
| Один формат вызовов | Прямой MCP + OpenCode Code Mode |
| Схемы инструментов зашиты в `system_prompt.txt` | Правила отдельно, схемы подставляются из живого MCP |
| `max_tokens` 512/1024 → ответ обрывался | 3072 токенов на ход |
| План терялся в `/v1/responses` при наличии tool_calls | План отдаётся отдельным `message`-item |
| CLI останавливался сразу после успешного `execute` | Цикл до 8 шагов: сборка → проверка → резюме |
| `look` возвращал base64 в контекст | Изображения сворачиваются в `[image: mime]` |

## Место на диске (минимальная установка)

Папка была 22 ГБ, после чистки — **~4.6 ГБ**. Удалено только то, что
восстанавливается и лежит в `.gitignore`:

| Удалено | Размер | Как вернуть |
| --- | --- | --- |
| `training/.venv` (torch/cuda/triton) | 5.8 ГБ | `tools/train_blender.sh` создаёт сам через `uv` |
| `target/debug`, `target/release/deps` | 2.8 ГБ | `cargo build --release` |
| Кэши базовой модели `q4/q4k/q8/q4km.ymq` | 5.4 ГБ | `yesman --dtype q4km --save-cache ...` (не нужны для BlenderMCP) |
| `Qwen2.5-1.5B-BlenderMCP/model.safetensors` | 2.9 ГБ | `python training/train_lora.py --merge-only` из адаптера |

**Оставлено (это и есть «основное для blenderMCP»)**: исходники Rust,
`models/Qwen2.5-1.5B-BlenderMCP/model.q4km.ymq` + tokenizer/config/шаблон,
базовая `model.safetensors` (нужна для переобучения), LoRA-адаптер
`training/output/lora_adapter`, датасет, `system_prompt.txt`,
`bpy_preamble.py`, `recipes.json`, оба release-бинарника.

Одной командой всё достраивается обратно (офлайн, без скачивания из HF):

```bash
bash tools/restore_from_minimal.sh
```

Если хочется срезать ещё **−2.9 ГБ** — можно удалить и базовую
`models/Qwen2.5-1.5B-Instruct/model.safetensors`, но тогда переобучение
потребует повторной загрузки базы (~3 ГБ, ~17 мин при их канале).
Для чистого инференса BlenderMCP она не нужна: работают только `.ymq` +
config + tokenizer + `bpy_preamble.py` + `recipes.json` + `system_prompt.txt`.

⚠️ После чистки `training/train_lora.py --dry-run` не запустится системным
`python3` (нет transformers). Либо восстановите venv, либо считайте
статистику через `python3 training/generate_3d_dataset.py --stats-only` —
она работает без зависимостей.

## Инференс

```bash
./target/release/yesman --cache models/Qwen2.5-1.5B-BlenderMCP/model.q4km.ymq --blender
./target/release/yesman-server --cache models/Qwen2.5-1.5B-BlenderMCP/model.q4km.ymq \
    --port 8000 --device cuda --ctx 16384
```

`--system` перекрывает правила из `system_prompt.txt`. Файл ищется относительно
текущего каталога, поэтому запускать бинарники нужно из корня репозитория.
